# shapelink — 支付链路流量特征混淆

Scala 3 实现的流量整形层，用于在银行与支付机构之间的加密链路上隐藏
**交易类型、金额区间、大客户资金动向**，同时满足三个硬约束：延迟预算、带宽成本、运维可排查性。

---

## 1. 先说什么做不到

这类方案最常见的失败不是技术实现，而是**承诺了不可能兑现的东西**。以下是明确的边界：

- **不能隐藏总吞吐量。** 如果某天交易量翻倍，链路总字节数一定翻倍。混淆改变的是"这些字节由几条消息、什么类型、多大金额组成"，不是"今天做了多少生意"。对抗这一点只能靠恒定速率发送，代价见第 6 节。
- **不能隐藏长期趋势。** 按小时/按天的聚合统计仍然可见。
- **不能对抗端点被控。** 如果攻击者能读端点内存，一切流量整形都无意义。
- **`fixed` 模式在默认参数下会把批量交易延迟推到秒级。** 这不是 bug，是权衡，见第 6 节。
- **不是对现有 TLS 的替代。** 本层建立在自己的 AEAD 之上（AES-256-GCM），用于点对点链路。它假设密钥已通过带外通道分发。

**最重要的一个结论**（来自第 6 节的实测数据）：**泄露与延迟是硬权衡，不能同时优化。** 把类别泄露从 55% 压到 1%，代价是批量交易 p99 从 0ms 升到 1.4 秒。任何声称"三个都变好"的方案都在某个维度上说了谎。

## 2. 核心设计：为什么填充信息必须藏在加密边界内

这是整个方案成立的前提，也是最容易做错的地方。

**如果帧头里写了长度、记录数、或"填充了多少字节"，填充就是自欺欺人**——攻击者直接读帧头就还原了原始长度。

因此本实现的线上格式是：

```
┌─────────────────────────────────────────────────┐
│ 固定 14 字节公开头                                │
│  version(1) | flags(1) | epoch(8) | seq(4)       │
├─────────────────────────────────────────────────┤
│ AEAD 密文（容量固定，AES-256-GCM）                 │
│  ├─ 明文区内：count(1) + N 条记录 + 随机填充      │
│  └─ 标签(16)                                     │
└─────────────────────────────────────────────────┘
总长 = cellSize，恒定。与业务消息长度、数量完全无关。
```

- **公开头没有任何变长字段。** 只有版本、标志、密钥纪元、序号。`core/Wire.scala:14` 处的测试锁定了这个契约，并注释说明：一旦帧头长出变长字段，填充就失效了。
- **消息数量、分片信息、填充量全在密文里**（`core/CellCodec.scala`）。填充字节是**随机**的而非零，所以即使有人拿到明文也无法靠字节模式区分填充与数据。
- **帧头绑定进 AEAD 的 AAD**（`core/Wire.scala:sealCell`），所以中间人改写 epoch 或序号会直接认证失败，不能重编号、拼接、截断。

实测：`immediate` 模式下线上出现 **1154 种不同的 cell 尺寸**；整形后是 **1 种**。

## 3. 延迟：单一 FIFO 是个陷阱

**这是开发过程中实测出来的最重要缺陷，值得单独说明。**

第一版用单一 FIFO 队列。60 事件/秒、25ms 截止时间、批量交易占 30% 时，实测：

```
latency_intr  p99 = 354.64 ms     ← 预算 25 ms
```

（注：这是修复前的旧实现在开发期测得的数字，当前代码已无法复现该配置。）

原因是**队头阻塞**：结算类的 24 条消息突发堵在队头，零售支付排在后面，被一个完全不相干的批处理任务拖了 350 毫秒。聚合数字（mean 68ms）看起来还行，但业务 SLA 已经崩了。

修复方式：**双队列严格优先级**（`shape/Shaper.scala`）。交互类（零售、查询）永远优先；批量类（结算、企业转账、外汇）只填充交互类用剩的容量。修复后同负载下：

```
latency_intr  p99 = 4.00 ms      ← 预算 25 ms，0 次逾期
```

这个设计同时是整形的手段：批量流量的宽松截止时间让它成为"理想的填充物"——它可以占用空闲时隙来压平线上速率，而不会耽误任何用户可见的交易。

`test("interactive latency is never sacrificed for bulk backlog (head-of-line isolation)")` 是这条的回归测试：它用同一个重批量负载配置，要求交互类 p99 在预算内且逾期为零。

## 4. 带宽成本

填充的代价是真实的。`--cell 1200` 时：

| 模式 | 带宽开销 | 说明 |
|---|---|---|
| immediate | 4.8% | 基线，无填充 |
| adaptive | ~22% | 合并小消息 + 空槽填充 |
| fixed + 2ms | ~61% | 恒定 500 cells/s |
| fixed + 1ms | ~80% | 恒定 1000 cells/s |

**在恒定速率模式下，增大 cell 反而让开销上升**——因为线上字节数 = cellSize × 固定速率，与业务量无关；cell 越大，每秒搬运的字节越多。实测（2ms 周期，300 秒）：

| cell | 开销 | 批量 p99 |
|---|---|---|
| 1200 B | 59.6% | 1233 ms |
| 2000 B | 75.7% | 494 ms |
| 4000 B | 87.9% | 204 ms |

所以 cell 尺寸是**用带宽换延迟**的旋钮，不是省带宽的手段。（在 `adaptive` 模式下方向相反：大 cell 能装更多消息，合并收益更大。不要在两种模式间套用同一个直觉。）

空流量时 `fixed + cover=always` 会持续按设定速率发送覆盖流量——这是恒定速率必须付的代价，不会因为你没交易就停止。1200B × 500/s ≈ 4.8 Mbit/s。

## 5. 运维可排查性

需求里这条最容易被忽略，但做错了会让运维绕过整个方案。

**问题**：整形之后，抓包看不到任何有用信息。运维遇到故障时，唯一"有效"的做法是打日志记录明文或原始长度——而这就把泄露原样还回去了。

**解法**（`ops/Diagnostics.scala`）：诊断信息走**加密信道内的独立逻辑流**，两端各自输出结构化日志。关键设计约束由类型系统保证：

```scala
final case class DiagEvent(
    atNanos: Long, node: String, kind: DiagKind,
    msgId: Long, corrId: String,        // 关联业务台账，不含身份
    epoch: Long, seq: Long, cells: Int,
    sizeBucket: String,                  // "le1k" 而非 "1023"
    latencyBucket: String,               // "lt5ms" 而非 "3.2ms"
    reason: String, detail: String
)
```

- **没有字段能携带 payload。** 不是"约定不写"，是结构上没有。
- **长度和延迟是分桶的**，不是精确值。因为诊断日志常常会流向共享 SIEM——精确值会变成一个新的旁路通道。这个细节由 `test("diagnostic records cannot carry payload and bucket their sizes")` 检查。
- 运维看到的是：`msg_id=42 corr_id=corr-1 kind=message_assembled size_bucket=le8k latency_bucket=lt5ms`。足够定位问题，不足以做流量分析。

## 6. 泄露量化：怎么测，测出什么

### 方法

`eval/` 下的对抗评估：

1. 把时间切成窗口（默认 1 秒）。
2. 每个窗口提取**只有线上可观测的**特征：cell 数量、字节数、到达间隔均值/变异系数/突发性、最大间隔、活跃占比、尺寸均值/变异系数、峰值密度（`eval/Adversary.scala:WindowFeatures`）。
3. 标签取窗口内**主导的交易类别 / 金额区间 / 是否含大客户事件**（来自仿真真值）。
4. 多项式逻辑回归攻击者，**按时间切分**训练/测试（前一半训练，后一半测试）。按时间切分是硬性要求——随机切分会让相邻窗口互相"记住"，虚高泄露（`test("windows are split by time, never at random")`）。
5. 报告准确率、多数类基线、宏 F1，以及**归一化互信息**：`残余泄露 = I(真实;预测) / H(真实)`，取值 [0,1]。

残余泄露 0% 表示攻击者的预测与真实标签之间的互信息为零——即窗口形状不携带该类信息。11% 表示仍能恢复约 11% 的标签熵。

### 实测结果（600–900 秒仿真，40 事件/秒，40 个随机种子中抽查 4 个，结论一致）

**允许突破速率（`--no-break` 关闭）：**

| 模式 | cells/s | rateCV | 开销 | 交互 p99 | 批量 p99 | 类别泄露 | 金额泄露 |
|---|---|---|---|---|---|---|---|
| immediate | 261 | **0.743** | 4.8% | 0.0 ms | 0.0 ms | **55.6%** | 21.4% |
| adaptive | 253 | 0.680 | 21.9% | 4.0 ms | 400 ms | 42.7% | 9.5% |
| fixed | 534 | 0.155 | 63.0% | 2.0 ms | 400 ms | 19.5% | 12.9% |

**禁止突破速率（`--no-break`）：**

| 模式 | cells/s | rateCV | 开销 | 交互 p99 | 批量 p99 | 类别泄露 | 金额泄露 |
|---|---|---|---|---|---|---|---|
| immediate | 261 | 0.743 | 4.8% | 0.0 ms | 0.0 ms | 55.6% | 21.4% |
| adaptive | 253 | 0.638 | 21.9% | 4.0 ms | 769 ms | 35.9% | 13.0% |
| **fixed** | **500** | **0.039** | 60.5% | **2.0 ms** | **1420 ms** | **1.1%** | **1.3%** |

最后一行是这套方案的能力上限：**线上速率完全恒定（500 ± 2 cells/s，CV 0.04），类别和金额泄露降到 1% 量级**——在 1 秒窗口上，攻击者从流量形状里几乎学不到任何东西。代价是批量交易 p99 达到 1.4 秒、7235 条逾期。

### 三个关键洞察

1. **只做合并不得要领。** `adaptive` 把尺寸压成 1 种，类别泄露反而从 55% 升到 42% 有限改善——因为窗口内的**总量速率**仍在泄露。攻击者不需要看单条消息，看一秒发了多少字节就够了。HTTP/2 的流量分析文献里这叫 volume-based fingerprinting，单纯 padding 对它无效。
2. **速率偏差（rateCV）是泄露的核心指标。** immediate 是 0.74，fixed+no-break 是 0.04。这两个数字的比值基本解释了泄露从 55% 掉到 1%。
3. **允许批量逾期抢发，等于把速率凸起送出去。** 上表 `--no-break` 与默认的唯一差别是批量记录到 398ms 是否允许无视令牌桶发送。允许 → 534 cells/s、泄露 19.5%；禁止 → 500 cells/s、泄露 1.1%。**那 34 cells/s 的超发就是泄露本身。** 所以 `breakRateForBulkDeadline` 默认 `true` 是个陷阱值，生产环境应该用 `false` 并接受批量延迟。

## 7. 怎么选工作点

不存在"最优配置"，只有"针对你的 SLA 的最优配置"。步骤：

```bash
# 1. 先用真实流量分布替换 sim/TrafficModel.scala 里的合成参数
# 2. 扫一遍工作点
sbt "run sweep --duration 900 --rate <你的均值> --no-break"

# 3. 对候选点做细看
sbt "run simulate --mode fixed --cover always --period 2 --no-break --duration 900"
sbt "run inspect  --mode fixed --cover always --no-break"   # 每个类别的窗口特征分布
```

判据（按优先级）：

1. **交互类 p99 ≤ SLA**（硬约束，`selftest` 会检查）。
2. **批量类 p99 ≤ 业务可接受值**。结算通常是分钟级，1.4 秒通常可以接受；如果是准实时结算，就不能用 fixed。
3. **rateCV 尽量低**。这是泄露的主要来源。
4. **带宽开销在预算内**。

典型选择：

- **零售为主、批量宽松** → `fixed, period=2ms, breakRate=false`。泄露最低。
- **有准实时批量结算** → `fixed, period=1ms`（开销升到 80%，但批量 p99 降到 335ms）。
- **带宽极紧** → `adaptive`，接受 35–43% 的泄露。

注意 "bandwidth" 在这里的含义：固定速率下**总带宽与业务量脱钩**。链路必须按峰值速率常驻容量，即使深夜没有交易。这是恒定速率的固有成本，不是实现缺陷。若链路容量无法常驻，就只能选 `adaptive` 并接受更高泄露。

## 8. 代码结构

```
core/          线格式与密码学
  Wire.scala       固定帧头 + AEAD 封装；保密边界的定义处
  CellCodec.scala  明文区记录打包/解包 + 随机填充
  Reassembler.scala 分片重组，带内存上界
  KeySchedule.scala 纪元密钥派生与轮换
  Crypto.scala     AES-256-GCM，nonce 由 (epoch,seq) 确定
  Rng.scala        SplitMix64，可复现

shape/         整形决策
  Shaper.scala     双队列 + 三种发送模式；全部延迟/带宽权衡在此
  ShaperConfig.scala 配置与 ServiceClass

sim/           可复现的合成负载与仿真
  TrafficModel.scala 交易类别/金额/突发模型
  Simulator.scala    虚拟时钟驱动的端到端仿真（含真实解密重组校验）

eval/          泄露量化
  Adversary.scala    窗口特征 + 逻辑回归攻击者
  Evaluator.scala    时间切分训练/测试、互信息、残余泄露

ops/           运维
  Diagnostics.scala  无 payload 的结构化诊断（加密流内）
  Metrics.scala      分服务类别的延迟统计

transport/     活链路
  ShapedPipe.scala   真实 TCP 上的整形收发
  LoopbackDemo.scala 回环端到端验证
```

## 10. 尚未实现 / 生产化缺口

诚实列出：

- **单向。** 目前是单方向整形。真实链路需要双向独立整形 + 双向密钥。
- **无握手。** 假设 master key 已带外分发，没有前向保密握手。生产环境应接入 TLS 1.3 或 Noise 协议作为密钥协商层，本层作为其上的记录层。
- **覆盖流量在 `fixed` 模式下是纯开销。** 没有做"用批量流量填充空闲槽位"的智能调度——第 3 节的批量填充在有空闲时有效，但完全空闲时仍然是纯覆盖流量。
- **对抗评估只用了逻辑回归。** 更强的攻击者（时序 CNN、随机森林、基于重尾分布的统计检验）可能找到更多泄露。残余泄露 1% 是"线性攻击者学不到"，不等于"信息论上为零"。
- **没有做多窗口/跨窗口特征。** 攻击者可以看 10 秒、1 分钟的模式，评估只做了单窗口。
- **流量模型是合成的。** 所有数字都是相对这个模型而言。上线前必须用真实分布重跑。
- **没有背压。** 如果对端不读，发送端只是靠 TCP 缓冲吸收；长时间背压会使队列无界增长（`max_queue_bytes` 指标会暴露这一点，但没有自动丢弃/告警策略）。

这些缺口里，**双向**和**握手的缺失**是距生产最远的两项。
